# Implementation Plan - Fix Main Window Navigation and Found Cue Data Focus

## Overview
Fix main window navigation flow and cursor focus behavior based on user feedback:
1. Remove focus/cursor from "Source cue details" so navigation flow is:
   `Cue Files` > `Search Results` > `Found cue data`
2. Position the cursor on the first line when focus enters "Found cue data" to enable immediate editing.

## Proposed Changes

### 1. UI Navigation & Cursor Updates: `UI/MainWindow.cs`
- In `_sourceDetailsTextView`:
  - Set `CanFocus = false` so "Source cue details" cannot receive keyboard focus and does not display a text cursor.
  - Set `_sourceCueDetailsPane.CanFocus = false` for completeness.
  - This ensures `Tab` advances directly from `_resultsListView` ("Search Results") to `_foundDetailsTextView` ("Found cue data"), and `Shift+Tab` navigates in reverse, skipping "Source cue details".
- In `_foundDetailsTextView`:
  - In `_foundDetailsTextView.Enter` event, position the cursor on the first line (`Y = 0`, at the end of the first line/artist value `X = firstLine.Length`) and set `TopRow = 0`.
  - Add helper `PositionCursorOnFirstLine()` and call it on `Enter` and when preview text is populated.

### 2. Unit Tests: `CueComplete.Tests/MainWindowTests.cs`
- Add unit test `MainWindow_Navigation_SourceDetailsCannotFocus_FoundDetailsReceivesFocusAndCursorOnFirstLine`:
  - Verify `SourceDetailsTextView.CanFocus == false`.
  - Verify `FoundDetailsTextView.CanFocus == true`.
  - Verify that when `FoundDetailsTextView` gains focus, `CursorPosition.Y == 0` (first line) and `CurrentRow == 0`.
  - Verify Tab navigation order advances from `FileListView` to `ResultsListView` to `FoundDetailsTextView`.

### 3. Verification & Packaging
- Run `dotnet test` to verify all unit tests pass.
- Run `dotnet build -c Release`.
- Run `dotnet publish -c Release -r win-x64 -p:PublishSingleFile=true --self-contained true`.
- Log progress in `.agents/progress.md`.
- Commit changes using Conventional Commits and push to the feature branch.
